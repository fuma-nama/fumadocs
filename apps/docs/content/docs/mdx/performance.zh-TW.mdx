## 概覽 [#overview]

Fumadocs MDX 是一個打包工具外掛，換句話說，它的效能瓶頸取決於底層的打包工具，上限也因此更高。

以 Turbopack 和 Vite 等常見的打包工具來說，它足以應付約 500 個以上 MDX 檔案的大型文件網站，幾乎能滿足所有使用情境。

由於 Fumadocs MDX 與您的打包工具協同運作，您可以在 MDX 檔案中匯入任何檔案，包括用戶端元件。
這提供了高度的彈性，並確保所有內容預設都經過最佳化。

### 開發伺服器 [#development-server]

分為兩類：

* **延遲 (Lazy)&#x20;**：Vite 等打包工具，以及 Node.js 與 Bun 等執行階段載入器，都能在模組被請求時 (例如呼叫 `await import()` 時) 按需編譯 MDX 檔案，因此開發伺服器的效能不太會受到 MDX 檔案數量影響。

  不過，請務必啟用[延遲載入](/docs/mdx/async)，延遲編譯才會生效。

* **預先編譯 (Precompiled)&#x20;**：Webpack 與 Turbopack 在開發模式下不支援延遲編譯，所有 MDX 檔案都必須事先編譯。視需要預先編譯的 MDX 檔案數量而定，開發伺服器可能會變慢。

  雖然這是打包工具層級的限制，但若您在意速度，我們建議改用[本機 Markdown](/docs/integrations/content/local-md)。它會略過打包工具層，在執行階段載入並編譯 MDX 檔案。詳情請參閱連結中的介紹。

### 圖片最佳化 [#image-optimization]

Fumadocs MDX 會透過 [Remark Image](/docs/headless/mdx/remark-image) 將圖片解析為靜態匯入。
因此，您的圖片會依據所使用的 React 框架自動進行最佳化 (例如 Next.js Image API) 。

```mdx
![Hello](./hello.png)

或放在 public 資料夾中

![Hello](/hello.png)
```

輸出結果：

```mdx
import HelloImage from './hello.png';

<img alt="Hello" src={HelloImage} />
```

### 正式環境建置 [#production-build]

在正式環境建置中，最耗時的部分通常是 TypeScript docgen (沒有 tsgo 時，TypeScript 編譯器的速度很慢) ，以及所有 MDX 檔案的零碎處理工作累加起來的時間。

在沒有快取的情況下，大量 MDX 檔案可能會導致建置期間的記憶體用量極高。原因如下：

* MDX 檔案編譯成 JavaScript 後，打包工具還必須再打包輸出的 JavaScript 檔案。
* 即使單一 MDX 檔案的編譯時間微不足道，累加起來仍可能相當可觀。例如約 2500 個檔案，假設每個檔案需要 25ms，冷建置最多將耗時 62.5 秒。

主要的解決方法是改為按需編譯，也就是只在內容被請求時才載入。

#### 本機 Markdown [#local-markdown]

如同開發伺服器一節的建議，[本機 Markdown](/docs/integrations/content/local-md) 是不錯的替代方案，它完全在執行階段運作，不需要額外的編譯工作。

#### 遠端來源 [#remote-source]

透過遠端載入內容的方式，建立您的自訂內容來源。

如果您的內容來源不需要預先編譯內容檔案，便可搭配 SSG 依需求處理這些檔案，進而**提升建置速度。**
不過，您將無法使用建置階段的最佳化 (例如打包) 。

如需實作自訂來源，請參閱[自訂來源](/docs/integrations/content/custom)。
